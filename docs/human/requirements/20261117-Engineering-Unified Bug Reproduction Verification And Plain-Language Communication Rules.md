# 关联设计

- 无。本需求仅更新工程协作沟通与疑似问题核实复现规范，不改变任何产品功能、界面表现或存量业务代码。

# 需求描述

1. **疑似问题核实与复现规范扩展至全协作阶段**：
   - 将原有的代码审查（Code Review）入口核实与复现先行要求统一扩展至所有协作阶段（包括理解对齐、根因排查、方案讨论与代码审查）。
   - 无论在何阶段提报疑似缺陷（含顺带排查出的潜在未暴露问题），均须先核对真实的界面文案、控件、快捷键与最新设计文档，直接剔除常规界面操作无法触发的纯理论分支。
   - 严禁顺着代码分支差异脱离真实界面编造假想操作场景；严禁将当前正常表现包装成缺陷（修改时的防退步约束须明确标注为现有正常表现）；严禁为论证重构合理性而强行编造缺陷凑数（单纯合并重复逻辑须如实表述为代码清理）。

2. **直白现象与真实操作步骤表达规范**：
   - 说明疑似问题或举例解释交互边界时，严禁用内部状态名称或实现机制黑话替代用户可感知的界面表现，严禁给简单操作编造冗余铺垫。
   - 凡提报疑似缺陷，须统一采用极简直白的三要素表达：一句话直述具体页面的问题现象、精确到真实界面控件与键鼠动作的复现步骤、以及预期表现与实际表现对比。

3. **延伸疑似问题先实测确认再纳入需求范围**：
   - 在理解对齐与方案讨论阶段，除已确认的主问题外，凡顺带排查出的其他疑似缺陷，须先单独给出具体复现步骤供人工实测验证；在人工实测确认复现之前，严禁直接将其写入需求范围或据此扩大修改范围。

# 验收标准

1. **工程协作规范同步无冲突**：项目工程协作规范与全局协作规则已同步将疑似问题前置核实、死分支剔除、直白复现三要素模板及人工实测前置隔离扩展至全协作阶段，与既有规范一致无冲突。
2. **存量代码与测试零改动**：本次仅更新工程协作规范文档，不改动业务源码与任何测试文件。
