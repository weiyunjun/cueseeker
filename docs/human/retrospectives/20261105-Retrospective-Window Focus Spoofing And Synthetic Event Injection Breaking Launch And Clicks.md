# 重大事故复盘：篡改窗口焦点与注入假鼠标事件导致应用无法启动显示及核心按钮瘫痪

## 1. 事故概述与严重程度

- **发现时间**：2026-11-05
- **影响版本**：2026-10-21 晚间至 2026-11-05 期间的主干构建版本（对比 2026-10-21 18:10 打包版本完全正常）
- **严重程度**：**致命级（P0，若已上线将导致产品完全不可用）**
- **故障表现**：
  将打包好的应用放到另一台 Mac 上运行时，出现三大致命故障：
  1. **每次启动均无法显示主界面**：双击启动应用后主窗口完全不出现，必须等待数秒后手动点击 Dock 栏图标才能唤出主界面（且每次启动 100% 必现）。
  2. **无法添加媒体源**：进入 File 页面点击“添加文件夹”按钮，下拉菜单完全不弹出。
  3. **无法打开设置**：点击顶部栏“设置”按钮，设置窗口完全不弹出。

## 2. 事故演进过程与根因复盘（“用新 Hack 修旧 Hack”的恶性循环）

经与正常工作的 `2026-10-21 18:10` 打包版本逐项比对，本次事故并非由常规界面控件或按钮样式引起，而是源于 **10 月 21 日晚 23:19 起，为了处理一个次要的视觉边界情况，违规篡改操作系统底层窗口与事件机制，随后在出现副作用时不断“用新 Hack 修补旧 Hack”**，最终导致系统窗口状态机与点击链路彻底崩溃：

1. **第一步（10 月 21 日 23:19）：为次要视觉细节篡改底层坐标并注入假事件**
   - **原始诉求**：当应用切到后台、窗口失去焦点时，清除已有的悬停高亮，且鼠标滑过后台窗口时不触发悬停高亮。
   - **错误做法**：没有采用系统原生的“仅在焦点窗口追踪”或纯业务状态层过滤，而是直接在窗口底层搞拦截——**当判断窗口未聚焦时，强行将窗口向系统上报的鼠标坐标篡改为屏幕外的 `(-10000, -10000)`，并在窗口焦点变化时，人为伪造一条“鼠标移出到 `(-10000, -10000)`”的假事件强行塞入界面容器**。

2. **第二步（11 月 1 日～2 日）：出现副作用后不拆源头，反而谎报系统焦点并在点击半途插队**
   - **暴露副作用**：第一步的底层拦截上线后，很快发现应用刚启动或刚切回窗口时，悬停高亮和右键菜单的二级子菜单频繁失灵。
   - **错误做法**：此时没有反思并拆除第一步的错误拦截，反而在窗口内部新增了一个自定义的“人为聚焦开关”，并**直接重写了 macOS 窗口系统的“是否为焦点窗口”只读状态——只要内部开关为真，就向操作系统谎报“本窗口已经是焦点窗口”**。
   - **雪上加霜**：为了在点击时“唤醒”这套自定义开关，又在窗口接收鼠标左键按下的入口处强行插队——**在鼠标左键刚按下、还没传给具体按钮之前，强行重跑窗口激活并广播焦点变化，直接触发第一步中“向界面塞入 `(-10000, -10000)` 假鼠标移出事件”的逻辑**；同时还将原本使用系统标准窗口的“设置”界面，也替换成了这套被篡改过焦点机制的自定义窗口。

3. **第三步（11 月 4 日）：启动前置重资源初始化，彻底引爆跨机死锁**
   - **导火索**：在应用启动创建主窗口之前，往主线程同步塞入了视频播放器内核与硬件渲染画布的预热初始化。
   - **三大故障的完整触发链**：
     - **启动主界面不显示**：在另一台 Mac 上，主窗口创建前的播放器与渲染画布同步初始化拉长了启动耗时，错过了系统赋予新启动应用的初始前台激活窗口期；随后窗口调用自定义激活逻辑，先把内部“人为聚焦开关”打开并向系统谎报“窗口已聚焦”，导致下一帧原本用于兜底的异步激活检查看到“已聚焦”谎报后**每次启动都 100% 跳过**，主窗口被永久留在后台。
     - **点击“添加文件夹”和“设置”无反应**：当用户被迫点击 Dock 图标把主窗口拉到前台时，走的是系统原生唤醒通道，窗口内部的“人为聚焦开关”依然为关闭状态（且全局外部点击监听随时将其清零），导致系统真实状态与内部开关彻底错位。此时用户去点“添加文件夹”或“设置”按钮，**在鼠标左键刚按下的瞬间（松开触发之前）**，窗口发现内部开关为假，当场插队重激活并往界面塞入“鼠标已飞出屏幕外 `(-10000, -10000)`”的假移出事件，直接把正在进行的按钮点击半途打断；而“设置”窗口本身也使用了谎报焦点的自定义窗口，导致两个核心入口彻底瘫痪。

## 3. 为什么开发本机与自动化测试完全漏检？

1. **开发本机热环境掩盖了启动时序差**：
   - 本机在开发环境下直接编译运行，系统缓存与显卡/音频驱动已充分预热，主窗口创建前的同步耗时刚好挤进系统激活时间窗内，掩盖了“谎报焦点导致兜底激活被跳过”的死锁分支。
2. **自动化测试依赖“测试专用后门”，沦为自欺欺人**：
   - 代码中为了给这套自定义门禁写单元测试，专门预留了“测试强制聚焦开关”和“测试强制鼠标坐标开关”。
   - 自动化测试在运行时直接打开这两个后门开关，完全绕过了 macOS 真实的窗口激活生命周期与真实的“鼠标按下 → 松开”事件派发链路。**测试通过只证明了“后门开关有效”，却完全漏掉了真实系统环境下窗口无法前置、点击被假事件打断的致命缺陷。**

## 4. 永久防范准则（工程红线）

为彻底杜绝此类足以毁掉项目的低级架构灾难，确立以下永久红线：

1. **严禁篡改或伪造操作系统底层状态与事件流**：
   - **严禁重写系统窗口的只读焦点/激活状态**（窗口是否为焦点窗口必须 100% 由操作系统真实状态决定，绝不允许用内部布尔值向系统谎报）。
   - **严禁篡改窗口鼠标坐标**（如返回 `-10000` 等屏幕外假坐标）或**向系统视图容器人为伪造、注入假鼠标/键盘事件**。
   - **严禁在鼠标按下的半途中插队执行窗口重激活或全局状态重置**，确保原生的“鼠标按下 → 鼠标松开 → 按钮触发”链路绝对干净。

2. **遵循奥卡姆剃刀，严禁“用新 Hack 修旧 Hack”**：
   - 原生系统已经天然提供的基础能力（如按钮按住移出边界松开不触发、焦点窗口追踪区域自动随焦点启停），必须优先使用系统原生标准机制。
   - 凡是需要在特殊状态下抑制悬停等视觉效果，**只允许在纯业务状态层做条件过滤，严禁去拦截或篡改底层窗口与事件通道**。
   - **一旦发现某个为视觉边界情况添加的门禁导致正常点击、聚焦或弹窗失灵，必须第一时间拆除原错误门禁**，绝不允许再叠加上百行新门禁去给旧门禁打补丁。

3. **主窗口启动首屏路径必须保持绝对纯净**：
   - 应用启动时必须第一时间创建并显示主窗口，任何非首屏必需的重资源初始化（如视频播放器内核、硬件渲染视图预热等）一律放在主窗口显示之后异步或按需进行，严禁阻塞首屏窗口的创建与系统激活。

4. **严禁在生产代码中埋设绕过真实交互链路的“测试后门开关”**：
   - 禁止为了迁就单元测试而在窗口或视图中增加“测试专用强制聚焦/强制坐标覆写属性”，防止测试与真实运行环境脱节。

5. **核心窗口与事件改动必须经过真实应用包冷启动验证**：
   - 凡涉及应用启动流程、窗口创建与激活、全局鼠标/键盘事件拦截的改动，必须以打包后的独立应用在真实启动与点击下的表现为准，严禁仅凭单元测试通过即认定安全。
