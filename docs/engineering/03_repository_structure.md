# Repository Structure

Status: Draft

## 1. Purpose

This document defines repository structure rules for CueSeeker.

It separates active native macOS implementation, archived Flutter code,
documentation, UI collaboration artifacts, scripts, and future support files.

## 2. Target Structure

The target repository structure is:

```text
CueSeeker/
  apps/
    macos-native/
  archive/
    flutter/
  docs/
    human/
      requirements/
      design/
        Design Index.md
        ui/
        data/
        workbench/
        playback/
    engineering/
      records/
    changelog.md
  ui/
    prototypes/
    references/
    assets/
  scripts/
```

Rules:

- Active app implementations belong under `apps/`.
- The native macOS rewrite must live under `apps/macos-native/`.
- Archived implementations belong under `archive/`.
- Project documentation belongs under `docs/`.
- UI collaboration artifacts belong under `ui/`.
- Project automation scripts belong under `scripts/`.

## 3. Active Application Code

`apps/` contains active application implementations.

Current active implementation target:

```text
apps/macos-native/
```

Rules:

- Native macOS app code must not be mixed into `archive/flutter/`.
- Flutter code must not be treated as active implementation code.
- New active app modules must be placed under the native app directory unless a documented architecture decision says otherwise.
- Build files generated by the native project should stay scoped to the native app directory when practical.

## 4. Archived Code

`archive/` contains old implementations retained for reference.

Current archived implementation:

```text
archive/flutter/
```

Rules:

- Archived code is read-only reference unless an explicit archival maintenance task requires edits.
- Archived Flutter code must not be imported by active native macOS code.
- Archived code may be consulted for schema, parsing, FTS behavior, playback experiments, and UX reference.
- Any behavior copied from archived code must be translated into the native architecture deliberately.

## 5. Documentation

`docs/` contains the sources of truth and implementation records for stable
project direction. Within it, `docs/human/` is the human-owned authority.

Expected structure:

```text
docs/
  human/
    requirements/
    design/
      Design Index.md
      ui/
      data/
      workbench/
      playback/
  engineering/
    records/
  changelog.md
```

Rules:

- Stable human-owned product meaning, UI specifications, and workflows belong in
  `docs/human/design/`.
- Each new change request belongs in `docs/human/requirements/` and should
  reference the relevant design rather than duplicate it.
- Engineering rules belong in `docs/engineering/`.
- AI implementation records belong in `docs/engineering/records/`.
- Milestone progress belongs in `docs/changelog.md`.
- AI-maintained project documentation must be written in English.
- Human-owned documents may use the human owner's chosen language and must not
  be modified by the AI.

## 6. Engineering Document Set

The formal engineering document set is:

```text
docs/engineering/
  00_project_governance.md
  01_documentation_rules.md
  02_git_workflow.md
  03_repository_structure.md
  04_architecture_rules.md
  05_database_rules.md
  06_testing_rules.md
  07_release_rules.md
  08_end_to_end_testing.md
```

Rules:

- Keep this rule set complete and aligned throughout formal native app
  development.
- Missing files in this set should be created as proper rule documents, not vague placeholders.
- If the formal structure changes, update `00_project_governance.md`, this document, and any affected references.

## 7. UI Collaboration Artifacts

`ui/` contains local UI artifacts used to align interface design before App
implementation.

Expected structure:

```text
ui/
  prototypes/
  references/
  assets/
```

Rules:

- Local HTML prototypes belong in `ui/prototypes/`, not under `docs/`.
- Visual reference material belongs in `ui/references/`.
- Shared prototype assets belong in `ui/assets/`.
- Stable UI requirements, component specifications, and workflows belong in
  `docs/human/design/ui/`.
- HTML prototypes should be treated as collaboration source artifacts. They are
  not substitutes for stable human-owned design documentation.

## 8. Scripts

`scripts/` should contain project automation.

Allowed examples:

- Development setup helpers.
- Database migration verification helpers.
- Fixture generation helpers.
- Release packaging helpers.
- Documentation consistency checks.

Rules:

- Scripts must not contain hidden product behavior.
- Scripts that modify user data must be clearly named and documented.
- Scripts used for release or migration must be deterministic enough to review.
- Generated artifacts should not be committed unless they are required source assets or documented release outputs.

## 9. Test Fixtures

Test fixtures should live with the native app test target or under a clearly named fixture directory once the native project exists.

Rules:

- Fixtures must not depend on the user's personal media library.
- Fixture media should be small and legally safe to store.
- Subtitle fixtures should include valid, malformed, multi-line, and CJK examples.
- Database fixture files must be isolated from production user databases.

## 10. Generated Files

Generated files should be kept out of version control unless they are required source artifacts.

Rules:

- Build outputs must not be committed.
- Local database files must not be committed.
- Local app logs must not be committed.
- Dependency cache folders must not be committed.
- Project files required by the native macOS app may be committed when they are part of the source project.

## 11. Repository Changes

Structural repository changes should be small and documented.

Rules:

- Moving major directories requires a clear commit and documentation update.
- Adding a new top-level directory requires a documented purpose.
- Removing archived code requires explicit approval.
- If implementation needs to diverge from this structure, update this document before or with the structural change.
